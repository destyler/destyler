> Step are used to guide users through a series of steps in a process.
> It's a great way to break down a complex process into smaller,
> more manageable step.

## Keyboard navigation

Give the step list an accessible name, for example by adding `aria-label="Checkout steps"`
to the element that receives `getListProps()`.
Render one native button trigger for every index from zero through `count - 1`; keep
the selected trigger mounted and enabled. Per-trigger native disabling and partially
mounted step lists are not supported navigation modes. Use `linear` to gate activation.

Steps use manual tab activation. Tab enters the list at the selected step. Left and Right
move focus between horizontal steps, with the direction reversed in RTL layouts. Up and
Down move focus in vertical layouts. Navigation wraps at either end; Home and End focus
the first and last rendered, enabled triggers. Arrow keys do not change the current step
or call `onStepChange`. Press Enter or Space on the native trigger button to activate the
focused step. Tab leaves the list, and returning to it starts at the selected step again.

In linear mode, inactive triggers expose `aria-disabled="true"`. Arrow keys can still
focus them so their labels and state remain discoverable, but activating them cannot
skip or revisit a step. Use the Next and Previous controls to move through the process.
In controlled mode, activation requests a change; the selected step and its content
change only after the parent accepts the new `step`.

The completion content at `index: count` is a terminal message, not a tab panel, because
it has no corresponding step trigger. Give it meaningful content or a heading. It remains
focusable, and the last real step is the list's fallback entry point when focus is outside
the list. All steps are complete and none is selected in this terminal state. This state
is a process summary rather than the usual active-tab/active-panel pattern. If your
application hides the element containing focus when advancing, move focus to an
appropriate visible heading or control as part of that transition.

## Setting the initial step

Set the initial step by passing the `step` property to the machine context.

:::tip
The value of the `step` property is zero-based index.
:::

```ts
const [state, send] = useMachine(
  steps.machine({
    defaultStep: 1,
  }),
)
```

## Controlled usage

Steps **step** index can be **uncontrolled** or **controlled**. Prefer `defaultStep` for an uncontrolled seed. Passing `step` into `machine(...)` is presence-controlled — sync with `onStepChange` and adapter `context`. See [Controllable State](/guide/controllable-state).

```ts
steps.machine({
  id: "1",
  count: 3,
  defaultStep: 0,
})

const step = 0 // your reactive state
steps.machine({
  id: "1",
  count: 3,
  step,
  onStepChange(details) {
    // details => { step: number }
  },
})
```

## Listening for step change

When the active step changes, the machine will invoke the `onStepChange` event

```ts
const [state, send] = useMachine(
  steps.machine({
    onStepChange(details) {
      // details => { step: number }
      console.log(`changed to ${details.step}`)
    },
  }),
)
```

## Listening for steps completion

When all steps are completed, the machine will invoke the `onStepComplete` event

```ts
const [state, send] = useMachine(
  steps.machine({
    onStepComplete() {
      console.log("All steps are complete")
    },
  }),
)
```

## Enforcing linear steps

To enforce linear steps, you can set the `linear` prop to `true` when creating the steps machine.
This will prevent users from skipping steps.

```ts
const [state, send] = useMachine(
  steps.machine({
    linear: true,
  }),
)
```

## Changing the orientation

The steps machine supports both horizontal and vertical orientations.
You can set the `orientation` prop to `horizontal` or `vertical` to change the orientation of the steps.

```ts
const [state, send] = useMachine(
  steps.machine({
    orientation: "vertical",
  }),
)
```

## Styling guide

> Earlier, we mentioned that each splitter part has a `data-part` attribute added to them to select and style them in the DOM.

```css
[data-scope="steps"][data-part="root"] {
  /* styles for the root part */
}

[data-scope="steps"][data-part="root"][data-orientation="horizontal"] {
  /* styles for the root part based on orientation */
}

[data-scope="steps"][data-part="list"] {
  /* styles for the list part */
}

[data-scope="steps"][data-part="list"][data-orientation="horizontal"] {
  /* styles for the list part based on orientation */
}

[data-scope="steps"][data-part="separator"] {
  /* styles for the separator part */
}

[data-scope="steps"][data-part="separator"][data-orientation="horizontal"] {
  /* styles for the separator part based on orientation */
}
```

### Current Step

To style the current step, you can use the `data-current` attribute.

```css
[data-scope="steps"][data-part="item"][data-current] {
  /* item styles for the current step */
}

[data-scope="steps"][data-part="separator"][data-current] {
  /* separator styles for the current step */
}
```

### Completed step

To style the completed step, you can use the `data-complete` attribute.

```css
[data-scope="steps"][data-part="item"][data-complete] {
  /* item styles for the completed step */
}

[data-scope="steps"][data-part="separator"][data-complete] {
  /* separator styles for the completed step */
}
```

### Incomplete step

To style the incomplete step, you can use the `data-incomplete` attribute.

```css
[data-scope="steps"][data-part="item"][data-incomplete] {
  /* item styles for the incomplete step */
}

[data-scope="steps"][data-part="separator"][data-incomplete] {
  /* separator styles for the incomplete step */
}
```
